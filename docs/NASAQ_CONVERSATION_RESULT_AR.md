# نَسَق: مسار المحادثة إلى التخطيط — 2026-10-09

**أصبح مسار مشروع ويب جديد قابلًا للاستخدام داخل الوكيل:** جمع متطلبات واستيضاح، ملخص قابل للتعديل، ترشيح واختيار واعتماد محدد، ثم موصل Spec Kit القائم، وحفظ المخرجات والحالة والاستئناف. هذا مسار تخطيط؛ لم يُبنَ موقع أو واجهة مستقلة أو محرك تنفيذ تطبيقات.

## كيف يستخدمه الشخص الآن؟

في جلسة جديدة داخل هذه المساحة، وجّه الوكيل إلى قراءة `skills/nasaq/SKILL.md` مرة واحدة، ثم تحدث معه عبر نَسَق. لا حاجة لأوامر Spec Kit أو إعداداته. مثال: «نسق، عايز مشروع ويب جديد لدليل استوديوهات التصوير، وأحب أرسل التفاصيل كلها معًا». أو `Nasaq, start a new web project for a photography studio directory.`

يفهم الوكيل الرسائل والمرفقات، ويعرض سؤالًا مؤثرًا أو ملخصًا بدل تكرار المعلومات المعروفة. يمكنك قول «عدّل المميزات»، «ارفض الترشيح»، «اختر ضمن هذه القيود»، «اعتمد التخطيط فقط»، «راجعني كل مرحلتين»، «توقف»، أو «أكمل». المساعد الداخلي يحفظ القرارات ويطبق بواباتها؛ لا يُطلب من المستخدم كتابة JSON أو تشغيل سكربتات.

نصوص الردود الفعلية والمراحل محفوظة في [محادثة الاختبار العربية](validation/conversation-transcript-ar.md) و[الإنجليزية](validation/conversation-transcript-en.md). **هذه محادثة نُفذت فعليًا عبر البرنامج برسائل مستخدم افتراضية معلنة، وليست تجربة مستخدم بشري مستقل.** مثال من السجل العربي:

> المستخدم الاختباري: «نسق، عايز موقع دليل لاستوديوهات التصوير.»
>
> نَسَق: «هل المشروع جديد أم قائم؟»
>
> بعد إرسال المميزات: «هل المفضلة مطلوبة رغم عدم وجود حسابات؟»
>
> المستخدم الاختباري: «احذف المفضلة، احتفظ بالقائمة والتصفية والتفاصيل فقط.»
>
> نَسَق يعرض الملخص المعدل، ثم يحفظ اعتماد المتطلبات. رُفض مصدر التصميم المرشح، وعدّل نَسَق الترشيح إلى التخطيط فقط. محاولة التشغيل قبل اعتماد نطاقه رُفضت. بعد الاعتماد استُخدم المصدر الأصلي.

## ما الذي يعمل فعلًا؟

- استقبال معلومات ناقصة أو مجموعة مميزات دفعة واحدة، وتسجيل المؤكد والافتراض والمؤجل ومصدر المعلومة. فهم اللغة واستخراج الحقائق والأسئلة يتم بواسطة الوكيل؛ المساعد لا يدعي محلل لغة طبيعي مستقلًا.
- اعتماد مرتبط ببصمة الملخص، وآخر للاختيار، وآخر لنطاق تشغيل التخطيط. التعديل المؤثر يبطل ما يتأثر؛ تكرار نفس الإجابة أو المقترح وتغيير لغة العرض لا يكرر التخطيط.
- اختيار المستخدم نفسه، أو قبول/رفض/تعديل ترشيح، أو تفويض الاختيار بقوائم تقنيات ومصادر وحدود صريحة. تضييق تفويض سابق يبطل اختيارًا مفوضًا لم يعد معتمدًا.
- عرض المرشحين وحالة الكتالوج ومستوى مراجعة الوثائق، وفصل ذلك عن تجربة Spec Kit المحددة القابلة للتشغيل محليًا. لا يُستدعى مصدر تنفيذ أو تصميم لمجرد ظهوره بالكتالوج.
- أنماط المراجعة الأربعة لمراحل التخطيط الست: بعد كل مرحلة، حتى رقم محدد، كل عدد مراحل، أو جميع المراحل المعتمدة. تغيير النمط لا يوسع الصلاحيات. الاستمرار لا يتجاوز حد «حتى المرحلة» دون تغيير صريح له.
- حفظ حقائق المشروع وموافقاته في `.nasaq/project.json`؛ أما حالات مراحل المصدر فتبقى في run.json الذي يديره الموصل القائم، دون نسخة أخرى من مدير المراحل.
- استئناف بعد توقف بين المراحل وبعد تسليم مرحلة مفتوحة قبل تقديم مخرجها. يعاد handoff نفسه دون إعادة سكربت المصدر، وتُفحص البصمات. إذا انقطع السكربت قبل حفظ handoff أو فشل، تُطلب معالجة صريحة ولا يُختلق نجاح.

## المصدر الذي استُخدم

**GitHub Spec Kit v1.1.2**، commit `959e866caa3618bf3dc290d5dca33394365af9c6`، عبر **workflow-reference**. أُعيد استخدام checkout المحلي المراجع ودليل التجربة السابقة دون تنزيل أو تثبيت جديد. الرخصة MIT وملفات المصدر والسكربتات وبصماتها موثقة في source-review وsource-lock المرتبطين بكل تشغيل.

شغّل موصل نَسَق الأصلي محلل القوالب وفحص المسارات وتهيئة الخطة والمهام والتحليل. لم يُبن بديل لمنهج المصدر. كل مرحلة تسلّم التعليمات الأصلية والطلب المعتمد للوكيل؛ يؤلف الوكيل الرد وفقها، ويرسله إلى `submit` ليكتب نَسَق الملفات ويسجل تسليمها وبصماتها. لا تدعي الأداة أن سكربت PowerShell يولد النصوص أو أنها استدعاء أصلي لمهارة المضيف.

أُنتجت لكل لغة مواصفات وخطة وبحث ونموذج بيانات وعقد ودليل تحقق مستقبلي و14 مهمة غير منفذة وتحليل اتساق. السيناريو دليل استوديوهات مقروء فقط، مختلف عن مثال الحجز السابق؛ لا مسار حجز ثابت في النتائج. [فهرس المخرجات والأدلة](validation/conversation-artifacts.md).

## العيوب التي ظهرت وما تغير

- كشف فحص الأدلة أن الكتابة النصية الافتراضية على Windows حولت LF إلى CRLF، فتطابقت بصمة النص المرسل مع النص المنطقي، لا بايتات الملف. صُحح التنفيذ ليحفظ UTF-8 دون تحويل أسطر، وأضيف اختبار يطابق البايتات نفسها. إيصالات الإصدار 2 تتطابق مباشرة مع الملفات. حُفظت إيصالات المراحل الأولى القديمة دون إعادة كتابة التاريخ؛ بصمات الملفات الفعلية كانت محفوظة أصلًا في run.json، ويختبرها الفاحص مستقلة عن بصمة النص المرسل القديمة.
- صُححت إبطاليات الاختيار: نفس المقترح لا يلغي اعتمادًا صحيحًا، وتغيير تفويض الاختيار يلغي الاختيار المفوض المتأثر. اختبارات صريحة تغطي الحالتين.
- حصل خطأ صياغة نص Python في مساعد حفظ رد التحليل داخل مجلد الاختبار؛ صُحح قبل إرسال الرد للمسار، دون تغيير توقعات اختبارات أو نتائج مرحلة.
- تحليل الوكيل النهائي وجد ملاحظتين منخفضتين: زيادة صراحة قيود بيانات المدينة في إحدى المهام، وحسم مصفوفة المتصفحات قبل التنفيذ. لا أخطاء حرجة أو عالية في مراجعة هذا السيناريو. تغطية 10/10 متطلبات/معايير للمهام حكم وثائقي، لا إثبات جودة تطبيق.

## ما لم يُنفذ وحدود النتيجة

لا بناء مواقع أو ربط تصميم/تنفيذ/قاعدة بيانات/اختبارات منتج بعد. المشروع القائم يوجّه إلى الفحص للقراءة فقط؛ لا تدعي هذه الدفعة اكتمال مساره. لا تحديثات مصادر أو forks أو تنزيلات جماعية أو تكامل أصلي لمضيف آخر.

الوكيل هو واجهة اللغة ومؤلف المخرجات ومراجعها في هذه التجربة، ولم نجر دراسة مستخدمين أو تقييمًا مستقلاً. الموافقات المحلية سجلات منسوبة لرسائل، لا تحقق هوية تشفيريًا أو sandbox؛ المضيف يبقى حد الصلاحيات. يوجد كاتب واحد؛ لا تشغيل متزامن أو عامل خلفي أو تنبيهات بعد انتهاء الجلسة. تعديل متطلبات بعد بدء التخطيط يحتفظ بالتشغيل القديم ويفتح مراجعة جديدة بعد الاعتماد، ولا يدمج تلقائيًا أجزاء مواصفات متغيرة.

## المرحلة العملية التالية المقترحة

اختيار ميزة صغيرة معتمدة من مشروع فعلي، ثم اختبار مصدر تصميم واحد من المرشحين الحاليين على مخرج واجهة وعقد بيانات واضح، يليه ربط تنفيذ مناسب للتقنية المعتمدة وفاحص واجهة/وظائف. تُختبر المناولة بين التصميم والتنفيذ والبيانات والتحقق لكل إضافة، وتظل جاهزية المرشح منفصلة عن نجاح التكامل. لا يبدأ ذلك أو يُثبت مصدر جديد ضمن هذه الدفعة.
