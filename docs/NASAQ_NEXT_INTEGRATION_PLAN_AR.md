تظل قيود الكاتب الواحد، غياب العامل الخلفي والتنبيه، والتعافي الصريح عند فشل/انقطاع السكربت قبل handoff قائمة. pause يمنع الأفعال التالية ولا يقطع عملية خارجية جارية. تُحفظ مشكلة إيصالات نهايات الأسطر التاريخية وحلها، وملاحظتا دقة مهام بيانات المدينة ومصفوفة متصفحات الإنتاج؛ لا تُحذف أو تعاد كتابة التجربة القديمة.

اختبار «الانقطاع» السابق أعاد الدخول عبر استدعاءات CLI منفصلة عند handoff محفوظ؛ ليس اختبار قتل العملية أثناء الكتابة أو انقطاع كهرباء. وفحص تغطية المهام يطابق معرفات ومتطلبات ووثائق مع تحليل الوكيل؛ ليس اختبار منفعة مستقلًا أو قبول تطبيق.

## هل يُستدعى نَسَق مباشرة؟

**بعد إعداد المهارة واختبار اكتشافها: نعم، هذا هو المسار المستهدف المدعوم بالمضيف، دون مطالبة المستخدم بقراءة الملف كل مرة. الآن: لم نثبت ذلك عمليًا.** المصدر موجود في skills/nasaq وليس في `.agents/skills/nasaq` داخل المساحة، ولا في مساري المستخدم المفحوصين `.agents/skills/nasaq` و`.codex/skills/nasaq`، ولا يظهر ضمن مهارات هذه الجلسة. openai.yaml يصف الواجهة ولا يثبت المهارة. وفق [وثائق OpenAI الرسمية](https://learn.chatgpt.com/docs/build-skills)، يقرأ المضيف المهارة عند استدعائها صراحة أو مطابقة وصفها؛ الاكتشاف الضمني ليس ضمانًا لكل صياغة.

ضمن التجربة المقترحة: إعداد محلي داخل **مجلد التجربة فقط** تحت `.agents/skills/nasaq`، بنسخة مضبوطة البصمات من المهارة الحالية، بلا تغيير إعدادات المستخدم العامة. اختبر جلسة مضيف جديدة بعبارتي «نسق، ابدأ مشروع حجز موعد» و`Nasaq, start a booking project` دون ذكر SKILL.md. ظهور المهارة ثم استخدامها وحفظ الحدث هو معيار النجاح؛ إن تعذر اختبار جلسة جديدة يُسجل البند محجوبًا لا ناجحًا. الإعداد العام للمستخدم خارج هذا التفويض المقترح.

## 1. الوظيفة ومعايير النجاح

مورد واحد ومواعيد ثابتة مجهزة للاختبار؛ اختيار موعد وحجزه ثم عرض رقم تأكيده. واجهة عربية RTL وإنجليزية LTR. لا حسابات أو دفع أو إشعارات أو إلغاء أو مدد مرنة أو نظام إدارة. بيانات وهمية بلا معلومات شخصية. لا حاجة لبحث منافسين لهذه التجربة التقنية.

- موعد متاح ينتج حجزًا محفوظًا وتأكيدًا صحيحًا؛ إعادة تحميل الصفحة وإعادة تشغيل الخادم لا تفقدانه.
- قيد UNIQUE فعلي على slot_id، مع موعد صالح وموجود. تجاوز الواجهة ومحاولة إدخال حجز ثانٍ يفشلان في قاعدة البيانات نفسها.
- طلبان متزامنان باتصالين مستقلين للموعد نفسه: HTTP 201 مرة و409 مرة، وصف واحد في قاعدة البيانات، بلا 500 أو database locked. كرر 20 زوجًا على مواعيد اختبار مستقلة مع بوابة بدء متزامنة وسجل الزمن؛ هذا إثبات نطاق صغير لا اختبار حمل إنتاجي.
- عقد صغير معتمد: GET المواعيد، POST الحجز، GET التأكيد بمعرف غير متسلسل؛ 400 للإدخال غير الصالح و404 لغير الموجود، مع CSRF للطلبات المغيرة. الواجهة تعرض التعارض وتسمح باختيار موعد آخر.
- اختبارات قاعدة البيانات وAPI والواجهة تمر، وتشغيل المتصفح على Chromium بسطح مكتب 1280×800 وهاتف محاكى 390×844 ولكلتا اللغتين؛ فحص لوحة المفاتيح والتسميات وحالات الانتظار والخطأ والنجاح. لا ادعاء اختبار هاتف فعلي أو جميع المتصفحات.
- بدء من نَسَق، توقف مقصود بعد التصميم واستئناف، وتغيير متطلب/تفويض يوقف التنفيذ المتأثر حتى اعتماده؛ الأدلة تكشف أي إعادة عمل. الاختبارات الـ114 السابقة تظل ناجحة مع الأدلة الأصلية محفوظة.

## 3. مرور المخرجات وأقل تطوير لازم

طلب نَسَق واعتماداته ← Spec Kit: spec/plan/tasks وعقد API ونموذج البيانات ← Impeccable: brief التصميم والحالات RTL/LTR ← اعتماد خطة التنفيذ والتصميم ← Django: قوالب وAPI ومهاجرات وقيد ← Django tests ثم Playwright ← تقرير تسليم.

ملكية واضحة: التخطيط يملك المتطلبات، التصميم يملك brief فقط، تنفيذ Django يملك الكود والمخطط، الاختبارات تملك أدلة التحقق. أي تغيير في العقد/النطاق يعود للاعتماد ويولد مراجعة جديدة؛ لا تعدّل مخرجات Spec Kit المكتملة في مكانها فتفسد بصماتها. احتفظ بمعرفات FR/AC/tasks عبر كل تسليم.

التطوير المقترح محلي ومحدود: إعداد مصدر مستقل عن مسار تجربة سابقة؛ اعتماد تنفيذ منفصل ببصمة يشمل المصادر والأوامر ومسارات الكتابة والمراحل؛ توسيع واجهة الجلسة والحالة القائمة بأوصاف مراحل التصميم/التنفيذ/التحقق بدل بناء مخطط أو مدير حالة موازٍ. لا تعمم STAGES الثابتة على نحو يكسر Spec Kit: يبقى تشغيله الفرعي المرجع لمراحله الست. لكل تسليم يُحفظ hash المدخل والمصدر والأمر الفعلي وcwd والخروج والمخرجات والاختبارات. نجاح exit code لا يكفي دون فحص العقد والقبول.

كل ذلك غير موجود الآن ويُختبر قبل تشغيل التطبيق. وحدات جديدة فقط عند حاجة واضحة، مع إعادة استخدام كتابة الحالة والأحداث والتحقق من المسارات. لا يدخل منطق «الحجز» في نواة نَسَق؛ هو ميزة التطبيق التجريبي.

## 4. اختبار نَسَق وحدود التنفيذ المقترح

الجذر المقترح `.nasaq-local/experiments/booking-integration-001/`، وتحته `sources/`, `.venv/`, `downloads/`, `cache/`, `browsers/`, `nasaq/`, `direct/`, `evidence/` وإعداد المهارة المحلي. داخل التطبيق: migrations وtemplates وstatic واختبارات وقاعدة SQLite وهمية. داخل الأدلة: طلبات وموافقات وحالة وقفل مصادر وتراخيص، logs، screenshots، traces، ونتائج المقارنة. سجلات الحالة المقترحة تظل `.nasaq/` تحت كل تشغيل. لا تُنشأ هذه التجربة الآن.

الموافقة المطلوبة تشمل جلب النسخ المحددة وwheels واعتمادياتها المذكورة وChromium الموافق لـPlaywright من مصادرها الرسمية، وحفظ caches وTEMP/TMP داخل الجذر، وتشغيل Python/Node المراجع والخادم على loopback فقط والمتصفح محليًا، وإيقاف الخادم عند انتهاء الاختبار. لا تغيير PATH أو إعدادات Codex العامة، ولا تثبيت عالمي أو npm install أو خدمة مدفوعة أو نشر أو مشروع منتج آخر. لا حذف قاعدة قائمة؛ إعادة الاختبار بقاعدة مؤقتة جديدة. أي أثر أوسع أو حاجة بناء حزمة من المصدر توقف لموافقة محددة.

قبل أي مصدر جديد: اختبر رفض التشغيل دون اعتماد، ثم مرره عبر فعل نَسَق الذي يتحقق من الاعتماد ويسجل التسليم **قبل** الاستدعاء. لا تشغيل منفصل ثم إلحاق تقرير. اختبر الاستئناف في عملية جديدة والحفاظ على بصمات المراحل المكتملة، ورفض تغيير المصدر/العقد بلا مراجعة، ورفض النشر حتى بوضع all. يبدأ الوضع الافتراضي بعد كل مرحلة رئيسية؛ تغيير الوضع لا يوسع أثر الشبكة أو الملفات المسموح.

## 5. المقارنة القابلة للقياس

زوج تشغيلات منفصل بعد الموافقة: مسار نَسَق في nasaq/، ومسار مباشر في direct/ يستعمل المصادر نفسها صراحة ويُعلّم أنه خارج نَسَق. نفس الطلب ومعايير القبول والمضيف/النموذج وإعداداته وإصدارات المصادر، وقاعدة فارغة لكل مسار؛ لا نسخ لكود التطبيق أو مخرجات الذراع الأول للثاني. اختبارات القبول المشتركة تُثبت مسبقًا. سجل ترتيب التشغيل؛ زوج واحد يعطي مؤشرًا لا برهان تفوق إحصائي.

نقيس: نجاح نفس معايير القبول، عدد تدخلات المستخدم وأوامر الأدوات التي اضطر لتعلمها، وقت الإعداد منفصلًا عن التنفيذ، وقت الاستعادة بعد توقف متماثل، المراحل المعاد تنفيذها، أخطاء تمرير العقود، اكتمال الأدلة، وعدد محاولات تجاوز الموافقة المرفوضة. تكلفة/رموز النموذج تُذكر فقط إن أتاح المضيف قياسها. رسائل مستخدم آلية تُعلّم fixtures ولا تستخدم لادعاء سهولة بشرية أو توفير وقت للمستخدم. النجاح المطلوب أولًا: قبول وظيفي مكافئ، وأوامر أدوات فرعية مطلوبة من مستخدم نَسَق = صفر، وأدلة كاملة واستئناف دون فقد؛ قد يضيف نَسَق زمن تحقق، ولا نفترض أنه أسرع.

## القرار المطلوب

اعتماد هذه التجربة المحلية بالمصادر والإصدارات والاعتماديات وآثار التنزيل والتشغيل والمقارنة المذكورة، مع مراجعة بعد كل مرحلة رئيسية افتراضيًا. اعتماد نظام الاستخدام المستهدف محفوظ بالفعل؛ لا نعيد طلبه. لم تتغير الشيفرة أو الاختبارات أو الكتالوج أو الأدلة السابقة في هذه المراجعة.
