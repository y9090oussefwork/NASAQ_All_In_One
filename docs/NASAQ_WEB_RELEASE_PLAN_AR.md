# خطة إصدار نَسَق للويب — NASAQ-WEB-RELEASE-1

**الحالة: مقترح للموافقة، وليس إذن تنفيذ. المراجعة: 2026-10-09، النسخة 1.**

هذه خطة إكمال منتج له نطاق دعم واضح، وليست سلسلة تجارب تتطلب موافقة بشرية بين مراحلها. بعد اعتماد الخطة وقائمة مصادرها وصلاحياتها، يكون نمط بناء نَسَق `all-approved`: تنفيذ، تحقق، إصلاح داخل النطاق، حفظ أدلة، ثم انتقال تلقائي. تجربة الحجز تصبح أحد اختبارات قبول المنتج؛ لا تصبح نواة نَسَق متخصصة في الحجوزات.

تتقدم هذه الخطة على اقتراح «مراجعة بعد كل مرحلة» في [البطاقة السابقة](NASAQ_NEXT_INTEGRATION_PLAN_AR.md). لا تلغي تقارير التجارب أو القيود أو مواصفات المستخدم؛ تخصّصها لنطاق الويب الحالي. تفويض بناء نَسَق نفسه منفصل عن موافقات مستخدميه في مشاريعهم.

## 1. تعريف الإصدار وما يعنيه اكتماله

المخرج المقترح **Nasaq Web 1.0.0-rc.1**، ثم 1.0.0 محليًا فقط إذا اجتاز جميع شروط الإصدار. منظومة تعمل داخل وكيل البرمجة، بلغتين، وتنسق دورة مشروع جديد أو تغيير مشروع قائم حتى تطبيق محلي قابل للتجربة وحزمة تسليم. تعتمد المصادر الأصلية، ولا تفرض مفتاح نموذج أو اشتراك إضافيًا أو واجهة ويب مستقلة.

اكتمال دورة الويب لا يعني اختبار كل إطار ويب موجود. نطاق التنفيذ والاختبار الإلزامي للإصدار:

| ملف العمل | متى يُختار | ما يجب تشغيله فعلًا |
|---|---|---|
| W1: ويب ثابت | محتوى/دليل بلا حسابات أو كتابات خادم | HTML/CSS/JS، تصميم، بناء/تقديم محلي مناسب، اختبارات سلوك ومتصفح وإتاحة؛ بلا قاعدة بيانات مفروضة |
| W2: تطبيق Django | تطبيق أعمال صغير/متوسط يريد تقليل الطبقات | Django Templates وForms/JSON API وORM وSQLite؛ مصادقة Django عند الحاجة؛ اختبارات ومعاملات وترحيل واستعادة |
| W3: React + Django API + PostgreSQL | واجهة تفاعلية تحتاج مكونات وحالة عميل وقاعدة مشتركة متعددة الاتصالات | React/TypeScript/Vite، Django API، PostgreSQL، عقود واختبارات بين الطبقات؛ لا Next.js أو خدمات سحابية إلزامية |

W1/W2/W3 ملفات اختيار قابلة لإعادة الاستخدام، وليست قوالب حجز ثابتة. لا تُفرض W3 على مشروع بسيط، ولا يُحوّل مشروع Django قائم إلى React. دعم المشروع القائم المثبت يشمل هذه الملفات؛ بقية التقنيات تُفحص وتُعرض فجوتها وتبقى `unsupported-execution` حتى اختبار محولها. لا إعادة كتابة Laravel/Vue/Next/FastAPI لإجبارها على ملاءمة نَسَق.

داخل الإصدار أيضًا: التثبيت الخاص بالمشروع، إعداد المصادر المختارة، التحديث المراجع والرجوع، إزالة الملفات المملوكة فقط، فحص البيئة، خرائط ومعرفة بمراجع، فحوص أمان وأداء وتشغيل محلي، توثيق وتوزيع محلي. دعم المضيفين المستهدف: Codex وClaude Code وCursor المحليون على Windows الحالي، مع مصفوفة أدلة فعلية لكل واحد. توفير شيفرة قابلة للنقل لا يعد اختبارًا على Linux أو macOS.

خارج الإصدار: Android وسطح المكتب، النشر الفعلي وإعداد السحابة/HTTPS العامة، المدفوعات والبريد/SMS والخدمات المدفوعة، Kubernetes والتوزيع متعدد الخدمات، مراقبة إنتاجية دائمة، تحديثات صامتة، كل مزودي المواصفات/الأطر، واجهة ويب لنَسَق، عامل يعمل بعد انتهاء المضيف، وإثبات امتثال أمني شامل. يظل التخطيط لهذه الاحتياجات ممكنًا مع تمييز فجوات التنفيذ، دون تشغيلها أو وعد بتغطيتها.

## 3. تجربة المستخدم النهائية

إعداد مرة واحدة خاص بالمشروع، ثم «نسق، أريد…» أو `Nasaq, …`. المضيف يقرأ تعليمات المهارة؛ المستخدم لا يحفظ أوامر المصادر أو يكرر طلب قراءة SKILL.md. إن أخفق الاكتشاف الضمني، يُعرض الاستدعاء الصريح لنَسَق نفسه الذي يدعمه المضيف، مع تسجيل إخفاق الصياغة الطبيعية.

المسار: فهم جديد/قائم ← جمع دفعة واحدة أو جولات قصيرة ومرفقات مسموحة ← استيضاح مؤثر وبحث منافسين عند فائدته وضمن صلاحية التصفح ← حقائق/افتراضات/مؤجل وملخص قابل للتعديل ← ترشيح تقنية ثم 1–3 بدائل مناسبة للتخصص وحالتها الفعلية ← اختيار يدوي/قبول/تفويض بقيود ← متطلبات وتخطيط ← تصميم وعقود وخطة تنفيذ ← اعتماد صريح أو مفوض داخل حدود معلومة ← تنفيذ واختبار وتقرير كل مرحلة ← تسليم قابل للتجربة.

يظل الوكيل واجهة الفهم والتأليف، وتكون النواة الصغيرة مسؤولة عن صحة الطلبات والبوابات والملكية والحالة والأدلة. لا يُبنى محلل لغة أو مولد مواصفات أو إطار agents منافس. البحث يستخدم أداة المضيف المتاحة؛ عند غيابها يطلب روابط أو يؤجل البحث، ولا يختلق منافسين. استيراد ملفات Markdown/JSON/TXT محدود الحجم والمسار أولًا؛ الصور عبر قدرة المضيف مع توثيقها؛ لا يعد نَسَق بمعالجة كل PDF/DOCX تلقائيًا.

الوضع للمستخدم يختار بين each / until / every / all-approved. المقصود بـall كل مراحل **الخطة المحددة المعتمدة** لا قبول تغييرات نطاق لاحقة. يستطيع تغيير التفويض أو المشروع أثناء العمل؛ يُحفظ الأثر ويوقف الجزء المتأثر عند حد آمن، ولا يعد بقتل عملية أو عكس أثر اكتمل. تصحيح محلي يحافظ على معيار القبول ضمن التفويض يمضي دون سؤال؛ تغيير قبول أو تكلفة أو معمارية غير مشمولة يعود لقرار الإنسان.

Node/Python الموجودان أرضية اختبار، لا شهادة خلو من ثغرات؛ إذا ظهرت حاجة تحديث runtime خارج هذه القائمة يتوقف الجزء المتأثر لقرار محدد، ولا تتغير إعدادات الجهاز خفية.

## 5. المعمارية التي سنكملها

نحافظ على `skills/nasaq/` كمصدر. يتدرج فصل ما يلزم من السكربتات الحالية إلى `scripts/nasaq_core/` خلف `scripts/nasaq.py`؛ تظل المداخل القديمة متوافقة إلى أن تُختبر الهجرة. لا refactor واسع لمجرد تحسين الشكل. اختيار Markdown/JSON/Python stdlib مستمر للنواة؛ pip/npm/Docker تحل وتجهز حزمها، وSpec Kit يملك وثائقه، والمضيف يملك أدوات اللغة والتعديل.

لكل تغيير: `project_id/change_id`، طلب معتمد، `selection`، `permissions`، `ownership`، مراجع المدخلات وبصماتها، مرحلة ومخرج وعقد، ودليل. `project.json` يشير للحالة، وrun.json الخاص بـSpec Kit يبقى مصدر حقيقة مراحله؛ لا نسختان قابلتان للتعديل للمتطلبات أو حالة المراحل. فصل الحالة حسب الميزة يمنع إبطال مشروع كامل بسبب تغيير واحد.

عقد المحول: detect/capabilities/plan_action/execute/collect_evidence/healthcheck، بحالات success/failed/blocked/unsupported. إدخال سجل لا يستورد أو يشغل المصدر. يسجل handoff قبل عمل الوكيل أو المصدر، ثم تُقبل الملفات من مساحة مرحلة مملوكة، وتُقارن العقود والفروق وتُشغل الاختبارات قبل اعتمادها. الادعاء بتنفيذ خارجي يحتاج الأمر/الأداة/نسخة المصدر/الدليل، لا مجرد وجود ملف.

مالك واحد لكل capability+component+phase، ومالك واحد لعقد API/schema/design tokens. المصمم يخرج brief وtokens وحالات؛ مطور الواجهة يلتزم بها؛ الخادم/البيانات يلتزمان بالعقد؛ المراجع لا يكتب كودًا دون تفويض. أي تغيير مؤثر يولد revision ويميز الأدلة stale. مصدر الحقائق موحد والتوليد باتجاه معلوم؛ لا نسخ مستقلة متعارضة.

## 6. المراحل المرتبة وبوابات قبولها

الجهد نسبي: **صغير** عمل محصور قليل التبعيات، **متوسط** عدة مكونات، **كبير** مسار متعدد الطبقات، **كبير جدًا** تقاطع مضيف/بيانات/تعافٍ وتقييم. ليست تقديرات أيام أو تكلفة مالية. في كل مرحلة: اختبار محدد أولًا حيث يثبت السلوك، ثم التنفيذ، ثم اختبارها وعدم الانحدار ذي الصلة، وتحديث الأدلة. المجموعة الكاملة بعد تغير النواة المشتركة وفي نهاية كل مرحلة، وقبل التغليف على النسخة النهائية. لا تؤجل الاختبارات حتى المرحلة الأخيرة.

- الوظيفة: تركيب المهارة من المصدر النهائي مرة واحدة، الاكتشاف الطبيعي والصريح، AR/EN، القيود والبوابات، انتقال جلسة واستئناف، تجربة نفس آليات التنفيذ دون إعدادات عامة.
- المصادر: وثائق Codex/Claude/Cursor الرسمية ونسخ المضيفين الموجودة أعلاه؛ لا تثبيت/ترقية مضيف. التبعية smoke من P2 ثم إعادة تحقق على P8.
- الملفات: hosts registry ومولد تثبيت واحد، `.agents/skills/nasaq` لـCodex، `.claude/skills/nasaq` لـClaude، `.cursor/skills/nasaq` لـCursor في **جذور اختبار منفصلة**، `docs/compatibility-matrix.md`, سجلات جلسات منقحة.
- القبول: المهارة تظهر وتُستدعى دون «اقرأ SKILL.md» كل مشروع؛ حالة ومخرجات فعلية تحت كل مضيف؛ لا تثبيت ثلاث نسخ يقرأها Cursor معًا. تُحفظ AGENTS/CLAUDE والقواعد الأخرى. يختبر أمر عربي وإنجليزي وموافقة ومنع كتابة واستئناف لكل مضيف.
- الاختبارات: جلسات مضيف حقيقية، لا mocks للـhost discovery؛ سجل host/model/version/OS/permissions. تجربة ثانية للإعداد/نموذج متاح ضمن الرصيد فقط، وعدم ادعاء دعم نموذج لم يُستخدم.
- الخطر/التوقف الضروري: حاجة تسجيل دخول أو حصة/صلاحية مضيف مفقودة. يكمل العمل المستقل وتبقى شهادة المضيف محجوبة؛ وجود حجب مطلوب يمنع إعلان اكتمال الإصدار الثلاثي ولا يُخفض الهدف صامتًا. الجهد: كبير متغير؛ حصة المضيف القائم بلا شراء جديد.

### P10 — القبول الشامل والمقارنة وتجربة الإنسان

- الوظيفة: تشغيل السيناريوهات في القسم التالي عبر مدخل نَسَق، إصلاح أي إخفاق داخل النطاق، مقارنة مع المصادر مباشرة، وتجربة استخدام إنسانية محدودة صريحة.
- المصادر: نفس الـlocks المعتمدة؛ لا مصدر جديد. التبعية P8–P9، وأدوات التحقق P7.
- الملفات: `tests/scenarios/`, `tests/agent-evals/`, `docs/validation/web-release/`, traces/لقطات/مخرجات وقائمة نتائج بعلامات التنفيذ/المحاكاة/المراجعة البشرية.
- القبول: جميع الرحلات الحرجة تمر على الكود النهائي، دون skipped كـpassed؛ المكتمل لا يعاد عند الاستئناف؛ معايير القبول لم تتغير لتناسب التنفيذ. أي فشل مؤثر يفتح العمل المعني ثم عدم الانحدار.
- الاختبارات: مصفوفة F01–F12، ثلاث مقارنات زوجية للطلب نفسه على الأقل عند توافر الحصة؛ إن قل العدد يذكر العدد الفعلي وحدود الثقة. جولة إنسانية AR وأخرى EN مع المستخدم/مختبر متاح؛ الرسائل الآلية المعلّمة ليست بديلًا عن هذا الدليل.
- الخطر/التوقف: التفاعل البشري أو حساب مضيف ليس مهمة يمكن اختلاقها؛ تجمع الطلبات اللازمة في جولة قبول واحدة، مع استمرار الفحوص المستقلة. الجهد: كبير جدًا ومتغير؛ أكبر مستهلك لحصة النموذج، دون تقدير tokens وهمي.

### P11 — حزمة توزيع نهائية وتوثيق وصيانة

- الوظيفة: حزمة من المصدر النهائي، أدلة ومصفوفة دعم وتتبّع متطلبات ودليل بدء عربي/إنجليزي وأمان ومساهمة وتغيير إصدارات؛ إرشادات بناء وتشغيل وترقية وإزالة بلا أوامر أدوات فرعية للمستخدم اليومي.
- المكونات: stdlib zipfile وتوليد من مصدر واحد؛ دون تضمين مهارات الغير أو binaries/venv/node_modules. التبعية جميع بوابات الإصدار المطلوبة، مع إمكانية تجهيز التوثيق مبكرًا.
- الملفات: `scripts/build_release.py`, `dist/nasaq-web-1.0.0-rc.1/skill.zip`, checksum/source manifest، `README.md`, `README.en.md`, `CONTRIBUTING*`, `SECURITY.md`, `THIRD_PARTY_NOTICES.md`, `CHANGELOG.md`, CI config محلي بلا تفعيل نشر.
- القبول: مدخل SKILL.md واحد، لا مسارات جهاز ثابتة ولا أسرار/أدلة خاصة، الحجم دون حد 25MB المستهدف أو إخفاق معلن، فك وتثبيت في مسار نظيف عربي بمسافات وتشغيل رحلة من الحزمة نفسها. الأرشيف التاريخي لا يُمسح.
- الاختبارات: reproducible build حيث يثبت، ownership/install/update/uninstall من الحزمة، روابط/JSON/لغة/UTF-8، scans للحزمة، اختبارات كاملة بعد آخر تغيير مؤثر. SHA النهائية تطابق ما اختُبر؛ أي تعديل لاحق يبطل دليله المتأثر.
- الخطر: رخص وأسماء أصحاب الحقوق قبل توزيع علني؛ MIT الحالي لشفرة نَسَق فقط. **النشر/رفع GitHub/سجل حزم ليس ضمن التنفيذ**. الجهد: متوسط، تكلفة تخزين محلي.

## 8. التنفيذ المتواصل وإدارة الفشل

بعد اعتماد هذه الخطة: يقرأ الوكيل build-state وآخر دليل، ينفذ المرحلة التالية المسموحة، يشغّل اختبارات المرحلة ثم عدم الانحدار، ويصلح الأسباب ضمن النطاق دون سؤال روتيني. يحفظ الفروق والأوامر والبيئة والبصمات والنتائج والقيود والخطوة التالية، ثم ينتقل إذا نجحت البوابات. تقارير التقدم معلومات وليست طلبات اعتماد جديد.

لا يكفي مرور وحدات adapter لإغلاق integration. الفشل يُصلح في التنفيذ؛ لا حذف اختبار أو تخفيض توقع أو تغيير نسخة مصدر لتجاوز المشكلة. failed/blocked/skipped/not_run/waived حالات منفصلة. تعذر جزء غير حرج لا يوقف العمل المستقل؛ تعذر شرط إلزامي يبقى مانع إصدار. لا إعادة محاولة للأثر غير القابل للتكرار قبل معرفة ما اكتمل منه.

يجوز تغيير ترتيب مهام أو دمج ملفات صغيرة وفق دليل جديد، بشرط تسجيل السبب والاعتماديات والاختبارات المتأثرة، وبقاء المصادر والصلاحيات والنطاق. التحول إلى إطار/محرك DB/مزود جديد أو تغيير قبول جوهري يحتاج قرارًا؛ حل bug وإعادة ترتيب داخلي لا يحتاجانه. إعادة التشغيل في جلسة أخرى لا تجدد طلب موافقة سارية، لكنها تتحقق من صلاحية اعتمادها وهوية المشروع والتغييرات.

لا daemon ولا وعد بعمل بعد انتهاء جلسة المضيف. عند حد الحصة/الجلسة يحفظ checkpoint ويصرح بالتوقف؛ يستأنف عندما تتاح الجلسة. خيارات each/until للمستخدم تبقى وظائف المنتج؛ **بناء هذا الإصدار نفسه يعمل all-approved بعد الموافقة**.

## 9. الصلاحيات التي تحتاجها الموافقة الواحدة

الموافقة المقترحة تشمل P0–P11 والمصادر المثبتة وسياسة اعتمادياتها، ولا تشمل نشرًا:

- قراءة/تعديل مصدر نَسَق الحالي واختباراته ومراجعه وبيانات جاهزية التكاملات اللازمة فقط، مع حفظ التعديلات والأرشيف التاريخي. كتابة fixtures/apps كأدلة في `.nasaq-local/web-release-1/`، وdocs/reports وdist داخل مساحة المشروع.
- جلب الإصدارات المحددة من GitHub الرسمي، PyPI/files.pythonhosted.org، registry.npmjs.org، مستودع Docker الرسمي وCDNs الرسمية اللازمة لمتصفحات Playwright. تثبيت محلي داخل venv/node_modules/bin/cache مع توجيه TEMP/TMP والمتصفحات إلى المساحة؛ لا تنزيل شامل للكتالوج.
- مراجعة الملفات والرخص والاعتماديات وسكربتات التشغيل قبل استخدامها، وتشغيل الأوامر المحددة عبر argv وtimeouts وcwd/مخرجات محصورة. إنشاء/إزالة ملفات اختبار مملوكة مؤقتة فقط بعد التحقق من مسارها، دون مسح أدلة القبول أو ملفات المستخدم.
- **استثناء معلن خارج مساحة الملفات:** pull الصورة المحددة إلى مخزن Docker القائم، وإنشاء حاويات/شبكات خاصة بالتجربة ومحدودة الموارد. لا privileged، لا تركيب Docker socket داخل الحاوية، لا mount لمشاريع أخرى، لا تغيير daemon أو تشغيله بامتياز إضافي، ولا system prune أو حذف حاويات/volumes غير مملوكة. DB ببيانات اختبار وloopback، وإيقاف الخدمات عند انتهاء الاختبار.
- تشغيل خوادم محلية ومتصفحات وفحوص أمان/حمل على أهداف loopback المعتمدة فقط؛ لا فحص مواقع خارجية أو إرسال بيانات عملاء. اتصالات advisory ترسل أسماء/نسخ الحزم العامة في fixtures والقفل فقط؛ تُراجع الحزمة الخاصة محليًا أو تُحجب دون إفشاء اسمها تلقائيًا.
- إعداد مهارات نَسَق داخل جذور الاختبار للمضيفين الموجودين، واستعمال الجلسات/الحصة الحالية لاختبارات القبول مع بيانات افتراضية. تشغيل مضيف قائم لا يثبت توفر حسابه؛ لا شراء أو مفتاح API جديد أو تجاوز موافقات المضيف. المستخدم قد يحتاج تسجيل الدخول/جولة القبول الإنسانية عند موضعهما.

تظل خارج التفويض: التثبيت العالمي وتغيير إعدادات الجهاز/المضيف العامة أو تحديثه، دفع اشتراك/شراء رصيد، النشر/إرسال رسائل للغير/رفع الشيفرة، تعديل مشروع منتج آخر، حذف بيانات حساسة، تغيير مصدر/معمارية جوهري خارج القائمة، أو بناء اعتماد Native من مصدر غير مراجع. الموافقات المحلية لا تتجاوز سياسة المضيف.

## 10. الجهد والتكلفة والاعتماديات الحرجة

المسار الحرج: P0→P1→P2→P3→P4→P5→P6→P7→P8→P9→P10→P11. توثيق P11 وsmoke المضيف P9 وفحوص الأمان P7 تبدأ مبكرًا، لكن إغلاقها النهائي بعد تكامل المصدر. هذه خطة عمل كبيرة متعددة الجلسات؛ لا يوجد أساس موثوق الآن لوعد بعدد أيام أو تكلفة نموذج ثابتة.

الأكثر كلفة نسبية: P1/P2 لصحة الحالة والتثبيت، P5/P8 لسلامة البيانات، P9/P10 لتفاوت المضيفين والتقييم المتكرر. تقدير تكلفة نقدية جديدة مستهدفة **صفر مشتريات**، لكنه لا يعني صفر استهلاك للحصة الحالية أو وقت الإنسان أو القرص والشبكة. حجم صورة PostgreSQL المعلن بالـregistry وقت القراءة 159,561,485 بايت، وهو حجم معلن للصورة فقط، لا تقدير مجموع التنزيلات أو استهلاكها على القرص. تقاس أحجام الحزم والمتصفحات والحصة والوقت عند الإعداد، وتوقف أي حاجة تكلفة جديدة.

أرقام أزمنة العمل/الرموز تسجل من التشغيل الحقيقي وتحدّث التقدير بعد P2/P5، دون إيقاف التنفيذ لطلب اعتمادها إذا بقيت داخل التفويض. عدم توفر مضيف/حصة/جلسة بشرية هو اعتماد خارجي معلوم، لا شيء نضمن حله بمجرد الاستمرار في كتابة الشيفرة.
