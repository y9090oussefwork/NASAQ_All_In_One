# Goo Engineering — دليل الاستخدام بالعربية

**الإصدار: 0.1.0 — أساس أولي قابل للتطوير، وليس منتجًا ثبت تشغيله على كل البيئات.**

تاريخ مراجعة مصادر الأدوات: 9 أكتوبر 2026.

## الفكرة

هذه Skill تنسّق دورة تطوير المشروع، بدل تكديس تعليمات وأدوات لا يحتاجها. تختار ملفات إرشاد مناسبة للمنصة والمخاطر: ويب، أندرويد، ويندوز، بوت تليجرام، خادم/API، أو أكثر من نوع في نفس المشروع. الأنواع الأخرى لها مسار تمديد، وليست مدعومة تلقائيًا بنفس عمق هذه المسارات.

الهدف هو برنامج يحقق متطلبات معتمدة، بتصميم مقصود وأمان واختبارات وأداء يمكن قياسها. لا يوجد وعد بمشروع مثالي أو خالٍ تمامًا من الثغرات، ولا بأن هذه التعليمات تستطيع إجبار أي نموذج على الالتزام. التنفيذ الحقيقي يعتمد على إمكانات بيئة البرمجة وصلاحياتها، وعلى الاختبارات والمراجعة وحماية المستودع.

## ماذا يوجد في الحزمة؟

`SKILL.md` هو ملف التنسيق الأساسي. مجلد `references` يحتوي قواعد متخصصة تُقرأ عند الحاجة، لا كلها في كل مهمة. مجلد `assets/templates` يحتوي نماذج المتطلبات والخريطة والتصميم والأمان والأداء والاختبارات والتشغيل. سجل `assets/tool-registry.json` يحتوي 34 أداة ومرجعًا مرشحًا بشروط اختيارها وروابطها الأصلية، وليس قائمة تثبيت أو موافقات مسبقة.

السكربت `scripts/engineering.py` يقدم أربع وظائف محددة: اكتشاف أولي للمنصات من ملفات المشروع، ونسخ محلي لهذه Skill، وإنشاء ملفات تخطيط جديدة دون استبدال الموجود، وفحص اكتمال هيكل الخطة. لا يتصل بالإنترنت ولا ينفّذ كود المشروع ولا يثبت الأدوات الخارجية.

## التثبيت المحلي

تحتاج Python 3.10 أو أحدث لاستخدام السكربت المساعد. فك ضغط `skill.zip`، ثم افتح الطرفية داخل مجلد `goo-engineering`. يجب أن يكون مجلد المشروع المستهدف موجودًا، وألا يكون داخل مجلد مصدر هذه Skill نفسها.

هذا مثال معاينة لتثبيت خاص بالمشروع في Cursor؛ استبدل المسار بمسار مشروعك:

```sh
python scripts/engineering.py install /path/to/project --agent cursor
```

بعد مراجعة الملفات المقترح إنشاؤها:

```sh
python scripts/engineering.py install /path/to/project --agent cursor --apply
```

القيم المدعومة لمعامل `--agent` هي `cursor` و`claude` و`codex`. المسارات التقليدية التي ينسخ إليها السكربت هي `.cursor/skills/goo-engineering` أو `.claude/skills/goo-engineering` أو `.agents/skills/goo-engineering`. في ويندوز ضع المسار بين علامتي اقتباس عند وجود مسافات، مثل `"D:\Projects\MyApp"`.

نجاح النسخ ليس إثباتًا أن الأداة اكتشفت المهارة وشغلتها. تحقق من ظهورها داخل إصدار بيئة البرمجة الذي تستخدمه، واستدعها بالطريقة التي تدعمها البيئة. يرفض السكربت استبدال تثبيت موجود؛ تحديث الإصدارات يحتاج مراجعة الفرق أولًا. اختُبرت عمليات النسخ محليًا على لينكس، وليس داخل التطبيقات الثلاثة نفسها.

لم تُنشر الحزمة على حساب GitHub. المجلد جاهز ليصبح مستودعًا بعد اختيار المالك والرخصة والخصوصية ومراجعة الملفات. لا يوجد رابط مستودع أو أمر تنزيل بعيد يتم الادعاء بأنه موجود.

## البداية في مشروع جديد

اكتب للأداة:

> استخدم goo-engineering لهذا المشروع. ابدأ باكتشاف المتطلبات على مراحل، ولا تبدأ تنفيذ التطبيق أو تثبيت أدوات خارجية قبل عرض الخطة والحصول على موافقتي. اسأل عن الفكرة والمستخدمين والمنصات والمميزات والقيود، وابحث عن بدائل ومنافسين عند الحاجة. اعرض بدائل التقنية والتصميم والأداء والاختبارات، مع سبب اختيارك وحدود التحقق المتاحة.

تقسم Skill الحوار إلى جولات قصيرة، مع إعادة استخدام الإجابات السابقة. تغطي الجمهور ومشكلة المنتج والمميزات والمستبعد منها، والأجهزة واللغات والاتصال والعمل دون إنترنت، والميزانية والموعد والنشر والبيانات الحساسة. البحث عن المنافسين اختياري، ويعتمد على مصادر عامة؛ عدم وجود دليل على ميزة لا يعني عدم وجودها.

ثم تقارن خيارات تقنية مناسبة، لا جميع اللغات في العالم. قد يكون القرار الصحيح تطبيقًا محليًا دون خادم، أو خادمًا بسيطًا دون Redis أو Kubernetes. المطلوب أقل تعقيد كافٍ لتلبية القيود، وليس أكبر عدد من الأدوات.

قبل التنفيذ، تنتج الخطة خريطة مميزات ومعايير قبول، وحدود المكونات وعقود البيانات وواجهات API، وخطة تصميم واختبارات وأداء ونشر. عند وجود واجهة، تُراجع اتجاهات بصرية وشاشات تمثيلية قبل بناء باقي الشاشات. يبدأ التنفيذ بجزء صغير يعمل من البداية للنهاية، ثم يتوسع بعد التحقق.

## البداية في مشروع قائم

اكتب للأداة:

> استخدم goo-engineering. ابدأ بفحص للقراءة فقط: لا تعدّل الملفات ولا تشغّل سكربتات المستودع ولا تثبت مكتبات. اعرض خريطة المكونات والمميزات والبيانات والاختبارات، مع مصدر كل استنتاج وما لم تتمكن من التحقق منه. بعد التقرير اسألني ماذا نُبقي أو نحذف أو نضيف أو نصلح أو نعيد تصميمه. لا تنفّذ التغيير قبل اعتماد الخطة.

يبدأ الفحص من تعليمات المشروع وملفات البناء والاعتماديات والكود والتوثيق الموجود. الخريطة الناتجة قد تكون جزئية، ويجب تمييز المؤكد من المستنتج والمجهول. تشغيل اختبارات أو سكربتات مستودع غير موثوق يحتاج مراجعة وإذنًا؛ القراءة فقط لا تعني تشغيل أوامر البناء.

بعد السماح بالتنفيذ الآمن، تُسجل حالة الاختبارات والبناء والأمان والأداء قبل التعديل. تُضاف اختبارات تثبت السلوك المهم، ثم تُنفذ التغييرات الصغيرة القابلة للرجوع. لا حذف جماعي اعتمادًا على تقرير كود غير مستخدم، ولا إعادة كتابة كاملة لمجرد تفضيل إطار جديد.

## التصميم والأداء والاختبارات

الهوية البصرية تشمل الهدف والجمهور وكثافة المعلومات وتسلسل الشاشات، ثم الألوان ذات المعاني والخطوط والمسافات وحالات العناصر. يُراجع وضوح العربية وRTL ومزج الأرقام والنصوص، وإتاحة الاستخدام والتنقل بلوحة المفاتيح وقارئ الشاشة، وحالات التحميل والفراغ والخطأ وضعف الاتصال. لا تُنسخ هوية المنافس، ولا يُفرض تصميم ويب على تطبيق ويندوز أو أندرويد.

يمكن اختيار Impeccable لتحسين الواجهات الويب، أو UI UX Pro Max للبحث في الأساليب والألوان والخطوط، أو frontend-design كبديل أخف. هذه مراجع مساعدة وليست حكمًا على جمال التصميم أو شهادة إتاحة استخدام. روابط المصادر داخل سجل الأدوات، ولا توجد ملفات خطوط أو نصوص مهارات خارجية مضمنة في الحزمة.

الأداء يبدأ بميزانية قابلة للقياس: زمن الاستجابة، واستهلاك الذاكرة والمعالج والبيانات، ووقت التشغيل الأولي، ومعدل الأخطاء والتكلفة. تُحدد بيئة القياس والحمل ونوع الجهاز وحجم البيانات. لا يكفي قول «يدعم عشرة آلاف مستخدم» دون تحديد معدل الطلبات والعمليات المتزامنة وتوزيعها وزمن الاستجابة المقبول.

الاختبارات تُختار حسب المخاطر والمنصة: وحدات ومنطق عمل وصلاحيات وعقود API وتكامل وقواعد بيانات وواجهة واختبارات بصرية وإتاحة استخدام. اختبارات التحمل تشمل عند الحاجة الحمل المتوقع والضغط والطفرة والاستمرار والتعافي. Playwright للويب، وMaestro لبعض تدفقات الواجهات المحمولة، وFlaUI لواجهات ويندوز، وk6 لحمل الخدمات، وSchemathesis لاختبارات API المبنية على مخطط. أدوات القياس الأصلية لأندرويد وويندوز لازمة لادعاءات الأداء على هاتين المنصتين.

لا تُنفّذ اختبارات ضغط أو هجوم على منافس أو خدمات تليجرام أو خادم خارجي غير مصرح به. تُستخدم بيئة يملكها المستخدم مع حدود واضحة للإيقاف وحماية البيانات.

## ذاكرة المشروع والقواعد الصارمة

المرجع المقترح هو `docs/engineering/INDEX.md` مع مؤشر قصير في `AGENTS.md` وحالة منظمة في `.engineering/project.json`. يمكن الاحتفاظ بمكان التوثيق الموجود بدل إنشاء مرجع مكرر. كل ميزة لها معرف يربط المتطلب بالكود والواجهة والبيانات والاختبارات. كل خريطة مهمة توضح مصدرها وإصدار الكود وآخر تحقق.

الأداة الجديدة تقرأ الفهرس والتغيير الحالي والجزء المتأثر، وليس كل المستودع دون داعٍ. لكنها لا تعتمد على ملخص قديم بدل مراجعة الكود الذي ستعدله. يجب تحديث المعرفة مع التغيير، لا إنشاء موسوعة في البداية وتركها قديمة.

ممنوع الادعاء بتشغيل اختبار لم يُشغّل، أو اعتبار فحص متعذر ناجحًا، أو تعطيل اختبار لإخفاء خطأ، أو إضافة مكتبة بلا مبرر، أو تغيير الصلاحيات والنشر وحذف البيانات دون تفويض مناسب. قرارات تثبيت الأدوات تشمل مراجعة المصدر والرخصة والصلاحيات والخطافات وإرسال البيانات والتكلفة وتثبيت إصدار معلوم.

هذه قواعد للـ Agent، وليست حواجز أمنية بذاتها. يجب تحويل ما يمكن منها إلى CI وفحوصات فعلية وحماية فروع ومراجعات وصلاحيات نظام تشغيل.

## استخدام الأدوات المساعدة

```sh
python scripts/engineering.py detect /path/to/project
python scripts/engineering.py scaffold /path/to/project --mode new --profiles web,backend
python scripts/engineering.py scaffold /path/to/project --mode new --profiles web,backend --apply
python scripts/engineering.py check-plan /path/to/project
python -m unittest discover -s tests -v
```

الإنشاء ينتج نماذج DRAFT غير معتمدة. فشل فحص الخطة قبل إكمالها متوقع. مروره لاحقًا يعني اكتمال الشروط البنيوية المعلنة فقط؛ لا يثبت جودة القرارات أو صحة التفويض أو نجاح اختبارات التطبيق.

## التحقق وحدود الإصدار

نجح 25 اختبارًا محليًا للسكربت المساعد على Linux وPython 3.13.5. التفاصيل في `VALIDATION.md`. توجد 11 حالة لتقييم سلوك النماذج، لكنها لم تُنفذ على Coding Agents في هذا الإصدار. لم تُشغّل بيئات أندرويد أو ويندوز، ولم تُنفذ اختبارات تطبيق حقيقي أو تثبيت الأدوات الخارجية أو قياسات أداء.

الخطوة الطبيعية التالية هي تجربة مضبوطة على مشروع واحد، وقياس جودة الخطة ودقة الخرائط والتغييرات غير المطلوبة والالتزام بالموافقات ونتائج الاختبارات، ثم تحسين المهارة وإصدار نسخة جديدة. إضافة ملفات أكثر لا تعني تلقائيًا مهارة أفضل.

المراجع الأصلية ومتى تختار كل أداة موجودة في `references/tool-catalog.md`. راجع شروطها وإصداراتها عند الاستخدام؛ تاريخ مراجعة التوثيق ليس ضمانًا بأن التكامل اختُبر أو أن الأداة آمنة.
