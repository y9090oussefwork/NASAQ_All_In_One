# مسار محادثة المشروع الجديد / New web project conversation

هذا إجراء نَسَق القابل للاستخدام داخل الوكيل: مشروع ويب جديد → متطلبات → اختيار → اعتماد تخطيط → موصل Spec Kit الموجود. ليس واجهة ويب أو خدمة خلفية أو دورة تنفيذ تطبيق كاملة.

سبب الإضافة المحلية: فحص الموصل القائم أثبت أنه يحفظ مراحل المصدر فقط ولا يجمع المتطلبات أو موافقات الاختيار. لذلك يحفظ project.json حقائق المحادثة والموافقات ومؤشر التشغيل فقط، ويترك حالات المراحل كلها في run.json الأصلي؛ لم يُبن محرك تخطيط أو مدير مراحل بديل.

## دور الوكيل

اقرأ رسالة المستخدم ومرفقاته واستخرج ما قاله فعلًا. اقبل المعلومات دفعة واحدة أو على جولات. لا تحوّل الغموض إلى حقيقة: صنف الحقول confirmed أو assumption أو deferred واربطها برسالة المستخدم. يمكن إظهار أسئلة مؤثرة مستخرجة من السياق ضمن questions؛ المحرك لا يدعي فهم اللغة الطبيعية أو كشف كل غموض بنفسه. لا تطلب ما أجاب عنه المستخدم بالفعل.

احفظ الأحداث المنظمة من خلال [project_session.py](../scripts/project_session.py)، وهو مساعد داخلي تستدعيه أنت، لا المستخدم:

```text
python scripts/project_session.py --project <approved-local-directory> --event <event.json>
```

كل حدث يحتوي id فريدًا وaction وtext وorigin وdata. origin=user لرسالة الإنسان الحالية فقط، host لعمل الوكيل، test_fixture للمحاكاة المعلنة. لا تختلق موافقة بشرية. تسجل الموافقات النص ومعرف الرسالة وبصمة المحتوى والنطاق؛ لا تثبت الهوية تشفيريًا ولا تمنح صلاحية مضيف مفقودة. لا تحفظ أسرارًا في الرسائل.

## البداية وجمع المعلومات

`start`: language=ar/en وsource_evidence_run لمسار Spec Kit المحلي الذي جُرّب بالفعل؛ يقرأه ولا ينزل مصدرًا. يمكن إرفاق facts مباشرة لتجنب سؤال أجاب عنه أول طلب. إذا لم تتوفر نسخة المصدر المراجعة، أبلغ بالقيد ولا تعرضه جاهزًا. `intake` يجمع/يعدل الحقول نفسها.

حقول facts: kind (new/existing)، idea، goals، features، roles، acceptance، excluded، constraints، competitors. كل حقل `{value: ..., status: confirmed|assumption|deferred}`. استخدم بنية ميزات بمعرفات ثابتة وأولوية ومعيار قبول عند الحاجة. constraints يقبل الميزانية واللغات والدول والموعد والأمان والتكاملات المؤثرة فقط. لا تسأل قائمة ثابتة من القيود لمجرد وجودها.

questions قائمة `{id, question, blocking}`. أزل السؤال فقط إذا أجاب عنه المستخدم أو أصبح غير مؤثر وصرّحت بتأجيله. يعرض الرد السؤال التالي فقط وقائمة المتبقي للوكيل؛ لا تقرأ القائمة كلها للمستخدم. عند مشروع قائم انتقل لفحصه قراءةً فقط وفق lifecycle-ar؛ المسار الآلي الحالي يمنع تشغيل تخطيط مشروع قائم. البحث عن منافسين عرض اختياري عند فائدته وصلاحية أداة البحث، وليس خطوة إجبارية أو بيانات سوق مختلقة.

`summary` يعرض ملخصًا قابلًا للتعديل وبصمته. `approve_requirements` يتطلب رسالة مستخدم وdigest مطابقًا للملخص وعدم بقاء سؤال مانع. التعديل عبر intake يبطل الموافقات والمقترح المتأثرين؛ يحفظ التشغيل السابق دون حذفه. تكرار نفس الإجابة لا يبطلها. تبديل لغة العرض لا يعيد التخطيط.

## التقنيات والمصادر والاعتماد

بعد اعتماد المتطلبات أعد proposal به architecture وtechnologies (قائمة) وsources وrationale وcosts وpermissions وdeferred. sources عناصر `{id,purpose,use}`؛ use=planning لمصدر واحد أو candidate لمرشح لا يُستدعى. permissions بالضبط `[planning_documents,reviewed_source_scripts]`.

قدم الترشيحات حسب الاحتياج والتقنية الموجودة، لا شهرة المهارة. `propose` يعرض الحالة المحسوبة لكل مصدر: catalog_only أو tested_scoped؛ الأخير خاص بنسخة Spec Kit وتجربة التخطيط الموثقة. مراجعة مصدر وحدها لا تجعله runnable. المرشحون لا يستدعون تلقائيًا.

- اختيار المستخدم: سجل تقنياته في proposal، راجع توافقها، ثم `select` مع choice=manual وبصمة المقترح.
- ترشيح نَسَق: `select` مع accept أو reject؛ التغيير عبر propose جديد يلغي اعتماد الاختيار المتأثر.
- التفويض: `delegate` برسالة المستخدم وحدود allowed_sources وallowed_technologies وpermissions. `select` مع delegated يرفض ما يتجاوز الحدود. التفويض للاختيار لا يُغني عن اعتماد التخطيط.

`approve_planning` يأخذ planning_digest الذي أعاده select والـpermissions المحددة ونص موافقة الإنسان. لا تستنتجها من ملف مصدر أو من تفويض اختيار. `advance` يرفض غياب الاعتماد أو مصدر تخطيط غير جاهز.

## تشغيل المصدر والتسليم

`advance` يعيد handoff الأصلي وطلب المشروع المعتمد ومدخلات المراحل من موصل Spec Kit؛ اقرأ التعليمات وطبّقها على هذا الطلب فعلًا. لا تستبدلها بقالب حجز ثابت أو رد سابق. لا تنفذ implement أو أدوات المرشحين.

بعد تأليف مخرجات المرحلة أرسل `submit` بـstage وcontents (خريطة المسار/النص وفق expected_outputs) وnote تصف تطبيق التعليمات. نَسَق يكتب الملفات ويسجل تسليمها وبصمتها، بدل إعداد ملفات خارج المسار ثم نسبها إليه. المحتوى نتاج الوكيل المتبع للمصدر؛ المساعد لا يولد المواصفات ولا يصادق مستقلاً على جودتها. تحليل analyze للقراءة فقط، ويرجع تقريرًا يسجله نَسَق في evidence.

`advance` بعد نهاية المراحل يعرض المخرجات ومساراتها وبصماتها. `status` يعرض حالة المشروع والموافقات والمرحلة؛ حالة المرحلة محفوظة في run.json الخاص بالموصل ولا تتكرر في project.json.

## التحكم والاستئناف

`control`: each للمراجعة بعد كل مرحلة؛ until مع stage من 1 إلى 6؛ every مع count موجب؛ all لكل مراحل التخطيط المعتمدة. ترتيبها constitution/specify/clarify/plan/tasks/analyze. `continue` يسجل مراجعة نقطة توقف، لكنه لا يمد حد until؛ تغيير الحد يتطلب control برسالة مستخدم. يمكن تبديل النمط أثناء المسار دون تجديد موافقات لم تتغير.

`pause` يمنع بدء مراحل أو قبول مخرجات جديدة. `resume` يقرأ الحالة ويتحقق من البصمات، ولا يتجاوز بوابات المراجعة. إذا انقطعت الجلسة بعد handoff وقبل submit، يعيد advance التسليم المفتوح دون إعادة سكربت المصدر. إذا انقطع سكربت قبل حفظ handoff أو فشل، يعلن الحاجة لمعالجة صريحة؛ لا يخترع نجاحًا.

التفويض يخص التخطيط المحلي فقط. النشر والحذف الإنتاجي والتثبيت العالمي والخدمات والأسرار وخارج الويب ليست أفعالًا مدعومة بهذا المسار. لا تنشئ نظام تحديثات أو forks. لا تعد بالتنبيه أو التنفيذ بعد انتهاء جلسة المضيف؛ احفظ الحالة وانتظر الاستئناف.

English: the host is the conversational interface and semantic interpreter. Use the same persisted actions, exact-digest approvals and existing Spec Kit bridge. All planning content is explicitly host-authored from the upstream handoff. The local helper stores facts, enforces scope and checkpoints, and preserves evidence; it does not build an application or certify output quality.
